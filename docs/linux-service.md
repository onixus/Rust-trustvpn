Собраны `dist/R-TrustTunnel-Linux-aarch64.flatpak` и
`dist/R-TrustTunnel-Linux-x86_64.flatpak` на Freedesktop 25.08.
x86_64 собран cross-компилятором и проверен под QEMU; его отчёт —

В реальном sandbox от UID 1000 проверены Wayland-окно и app ID, страницы
настроек, StatusNotifier-регистрация/меню/скрытие/восстановление окна. Проверена
цепочка Flatpak → системная D-Bus-служба root → приватный FD → maintenance lease;
чужой UID отклонён. В разрешениях нет X11, host/home filesystem или устройств.
Профили передаются через закрытый сокет, а не сообщения D-Bus.

Повторяемые проверки: `ci/flatpak_smoke.py --installation ci` и контейнерный
`ci/flatpak_service_smoke.py --installation ci --user rtrust-test`. Стенд —
Weston headless, не Plasma/KDE. Результат и хеш пакета сохранены в
`reports/flatpak-runtime/acceptance.json`.

Для host broker нужны `deploy/org.rtrusttunnel.Service.conf` и переменная
службы `RTRUST_DBUS=1` (drop-in `deploy/rtrust-flatpak.conf`). GUI-установщик
host-службы пока не готов. Не завершены проверка физического KDE,
Background portal, файловый portal, сохранность vault через реальный Secret
Service, подписанный репозиторий и install/update/rollback host-пакета.
Следующий раздел описывает прежний отдельный native preview, не установку Flatpak.

Дополнительно доступен [режим всего компьютера: IPv4 + DNS и nftables kill switch](linux-full-tunnel.md). Ниже описан режим выбранных сетей.

Development preview, 30 сентября 2026. Native-приложение работает от обычного пользователя; отдельная Rust-служба создаёт TUN и маршруты. Официальный TrustTunnel CLI не запускается. Поддерживается один desktop UID на машину и одна активная сессия. На Windows также доступна [Wintun-служба](windows-service.md); macOS поддерживает [системный VPN](macos-system.md).

## Установка и использование

Требуются Linux с systemd, iproute2 (`/usr/sbin/ip`), `/dev/net/tun` и сервер с поддержкой HTTP/2. Соберите `cargo build -p rtrust-tun -p rtrust-native --locked` либо используйте соответствующую архитектуре preview-сборку. Из корня проекта:

```sh
sudo sh scripts/install-linux-service.sh "$(id -u)" target/debug/rtrust-service
# GUI запускается без sudo:
target/debug/rtrust-native
```

В готовом пакете `dist/service-preview-linux[-x64]` запустите `sudo sh ./install-linux-service.sh "$(id -u)" ./rtrust-service` из каталога пакета. Linux ARM64 проверен VPN E2E; x86_64 прошёл cross-build и Wayland GUI/CLI smoke под amd64-эмуляцией. Installer копирует бинарник и unit, включает и перезапускает `rtrust-service@UID.service`. Установщик отказывает при активном VPN, аварийном журнале или включённом always-on. Перед атомарной заменой бинарника старая служба останавливается, затем журнал проверяется повторно. Это отдельный установщик службы, не финальный мастер установки приложения.

В настройках подключения выберите **TUN · выбранные IPv4-сети**, введите CIDR через запятую или пробел и нажмите верхнюю кнопку подключения профиля по умолчанию. Например, `10.20.0.0/16, 203.0.113.7/32` — только если эти сети действительно нужны и доступны через ваш endpoint. Поле не заполняется автоматически из импортированной route policy; режим, CIDR и порт SOCKS5 сохраняются вместе с профилями по кнопке «Сохранить шифрованно» и автоматически загружаются при следующем запуске. Подключение не запускается автоматически. Настройки общие для приложения, а не отдельные для каждого профиля.

Разрешено 1–16 непересекающихся канонических IPv4 CIDR с префиксом /8–/32. Default route, loopback, link-local, multicast/reserved и сети с локальными адресами интерфейсов отклоняются. Служба отказывает при конфликтующих policy rules, занятой таблице или интерфейсе. Используются `rtrust0`, адрес `169.254.254.2/32`, таблица `51830`, priority `10530`.

## Область действия и ошибки

Маршруты применяются только к исходящему IPv4-трафику указанного UID в выбранные сети. Служба работает от root, поэтому её транспорт до endpoint не попадает в эти маршруты. Трафик других UID, root/setuid-программ, контейнеров и пересылаемый трафик не покрывается. **Это не защита всего системного трафика.** IPv6, ICMP, фрагментация и управление DNS ещё не поддерживаются. Системный resolver не перенастраивается: DNS от отдельной службы resolver может идти напрямую даже при выбранной IPv4-сети.

В таблице присутствует `unreachable default`: при потере TUN выбранный трафик не переходит на обычный default route. Потеря endpoint переводит сессию в состояние блокировки и запускает автоматическое переподключение. Интервалы повторных попыток — 2, 4, 8, 16 и максимум 30 секунд; каждая попытка ограничена 30 секундами. После 30 секунд стабильной работы интервал сбрасывается при следующем сбое. Правила и unreachable route остаются на месте; восстанавливаются только маршруты к новому TUN. Старые TCP/UDP-потоки не возобновляются: приложения должны открыть новые соединения. Нажатие «Отключить» сначала отменяет переподключение, затем удаляет правила и маршруты, дожидается ACK и возвращает обычную связность. Последующее восстановление endpoint не подключает клиента снова.

Закрытие GUI или потеря его IPC-соединения освобождает сессию и восстанавливает маршруты. Это намеренное поведение preview, а не постоянный kill switch. SIGTERM службы выполняет очистку. При SIGKILL/аварии службы правила и блокировка сохраняются; после её перезапуска нажмите **«Сбросить блокировку после аварии»** в TUN-настройках. Восстановление возможно без подключения к endpoint. Журнал `/run/rtrust/lease.json` содержит только UID и CIDR, имеет права 0600 и сохраняется при неполной очистке. Перезагрузка ОС очищает runtime-журнал и непостоянные правила; автоподключения и защиты до входа пользователя нет.

Служба не хранит профиль на диске. Для переподключения профиль остаётся в памяти на время активной сессии; секретные поля обнуляются при освобождении. После перезапуска самой службы профиль автоматически не восстанавливается. Unix IPC проверяет SO_PEERCRED с обеих сторон: GUI принимает root-сервер, служба — только настроенный UID. Другие процессы того же UID также могут управлять службой. Каталог сокета принадлежит root; кадры имеют лимит размера, версию и ограничение времени первоначального чтения. Одновременно допускается до 16 обработчиков IPC, активная сессия одна. Сетевой стек сейчас тоже находится в root-процессе; дальнейшее разделение привилегий ещё не реализовано. Systemd unit ограничивает capabilities до CAP_NET_ADMIN и доступ к файловой системе/устройствам.

## Проверка

`scripts/service-interop.py` запускается только внутри disposable root Docker-контейнера с NET_ADMIN, SYS_ADMIN, `/dev/net/tun`, Python 3, OpenSSL, curl и iproute2. Нужны собранные `rtrust-service`, `rtrust-inspect` и официальный endpoint 1.1.0 соответствующей архитектуры:

```sh
cargo build -p rtrust-tun -p rtrust-inspect --locked
python3 scripts/service-interop.py /absolute/path/to/trusttunnel_endpoint
```

На Linux ARM64 проверены реальные 512 KiB HTTP через TUN, изменение source address, разделение UID 1000/1001, отказ чужому UID, версия/лимит кадра, запрет второй сессии, Stop ACK и восстановление. SIGKILL службы проверяется при существующем прямом default route: выбранный UID заблокирован, другой UID доступен, перезапуск сохраняет блокировку, авторизованный Recover снимает её. Проверены два последовательных падения/восстановления endpoint: блокировка во время повторных попыток, реальный HTTP после автоматического восстановления, отсутствие дублирующихся правил и отмена переподключения при Stop. Клиент теста использует тот же Rust IPC-код, что и GUI. Повторно пройден [полный data-plane стенд](tun-preview.md): TCP/UDP/DNS, параллельные загрузки и half-close.

Запуск GUI на KDE и полный lifecycle установки под systemd в этой итерации не проверены: служба в тестовом контейнере запускается напрямую. Production-сервер не изменялся.
